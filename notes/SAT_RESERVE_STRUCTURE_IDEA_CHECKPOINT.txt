SAT reserve-loss experiment checkpoint

Purpose
--------
We are studying recursive scaling for SAT cluster selection.
Main question:
    When IG drops at level 5, can reserve recover useful_IG and reduce D?

What already looks stable
-------------------------
1. G beats L on all tested tasks.
2. D = H / useful_IG is a useful predictor.
3. danger_rate stays around 3-4% across levels and n.
4. Recursive clusters reduce D.

Current problem
---------------
For larger n, level-5 clusters become too large.
Observed example:
    n=2000 level5 IG=38 < level4 IG=42

Reserve idea
------------
Base formulas:
    base_useful_IG = IG * (1 - danger_rate)
    loss = IG * danger_rate
    reserve[var] += part of loss for dangerous variables

Recovery formula:
    recovered = (0.5 ^ level) * overlap * reserve_score
    useful_IG_reserve = base_useful_IG + recovered
    cap: recovered <= IG

Reserve is memory, not fuel:
    reserve is not decreased after use.

Why the first version failed
----------------------------
overlap was often 0 because reserve and cluster construction were independent.
That meant reserve existed, but clusters did not move toward dangerous variables.

Current fix
-----------
Make clustering reserve-aware:
    when building clusters, prefer units / variables with higher reserve_score.

Implementation direction:
    cluster merge priority = co-occurrence signal + reserve_score bias

Expected effect:
    clusters should contain dangerous variables more often,
    overlap should increase,
    recovered should become non-zero and more useful.

Files involved
--------------
    sat_recursive_cluster_levels.py
    sat_reserve_loss_probe.py

Important code changes already made
-----------------------------------
1. build_next_level now accepts optional reserve-aware inputs:
       unit_scores=None
       reserve_bias=0.0

2. In reserve mode, sat_reserve_loss_probe computes unit_scores from current reserve
   and passes them into build_next_level.

3. baseline and reserve now use the same sampled candidate set,
   so paired comparison is fair.

4. A paired summary is written for direct comparison:
       sat_reserve_loss_probe_step2_paired_summary.csv

5. Added CLI parameter:
       --reserve-bias
   default:
       0.35

How the clustering bias works
-----------------------------
The merge priority is adjusted roughly as:
    adjusted = cooccur_count + reserve_bias * (score_a + score_b)

Eligible edges are still filtered by min_cooccur first.

Current test protocol
---------------------
Run the same benchmark:

    python sat_reserve_loss_probe.py --sizes 1000 2000 --formulas 3 --max-levels 5 --min-cooccur 2 --base-max-cluster-size 8 --sample-units 500 --beta 0.5 --reserve-bias 0.35 --out-prefix sat_reserve_loss_probe_step2

Then compare:
    baseline_useful_IG vs reserve_useful_IG
    baseline_D_pred vs reserve_D_pred
    delta_useful_IG in paired summary

Success criteria
-----------------
At levels 4-5:
    reserve_useful_IG > baseline_useful_IG
    reserve_D_pred < baseline_D_pred
    delta_useful_IG is positive in paired summary

If it still fails
-----------------
Try one of these:
    increase reserve_bias
    make reserve influence merge order more strongly
    use reserve also in candidate ranking, not only clustering
